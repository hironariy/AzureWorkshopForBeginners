# 第4回 Azure コンテナサービス紹介、Azure Container Instances をつかった Web サーバ構築 ドラフト

## 表紙

- 講座名: Azure Workshop for Beginners
- 回: 第4回
- タイトル: Azure コンテナサービス紹介、Azure Container Instances をつかった Web サーバ構築
- 形式: オンライン座学 + ハンズオン
- 時間: 60分 (50分レクチャー/ハンズオン、10分QA)
- 想定日: 2026年7月9日

## この回の位置づけ

第4回は、第3回で Azure VM 上に Web サーバを構築した経験をもとに、コンテナを使うと何が簡略化されるのかを体験する回です。
第3回では VM、OS、ディスク、NIC、Public IP、NSG などを意識しました。本回では、講師が用意したコンテナイメージを Azure Container Instances に配置し、インターネットから NGINX にアクセスできることを確認します。

ACI は、コンテナをすばやく単体実行するためのシンプルなサービスとして扱います。第5回以降で使う Azure Container Apps や ACR への橋渡しとして、コンテナイメージ、レジストリ、実行環境の関係を理解することを重視します。

## 受講前提

- 第2回で Web 3層アプリケーションの基本を学んでいることが望ましい。
- 第3回で Azure VM を使った Web サーバ構築を体験していることが望ましい。
- Azure Portal でリソースグループを作成し、リソースの Overview を確認した経験があることが望ましい。
- Dockerfile の作成やローカル Docker 操作の経験は不要。
- 受講者には、講師が用意する Azure サブスクリプションをスコープとして Contributor ロールが付与されている。
- 受講者番号として `s01`、`s02` のような値が講師から案内されている。
- 講師から、共有 ACR のログインサーバー名、イメージ名、タグ、必要な参照方式が案内されている。

## 到達目標

- コンテナ、コンテナイメージ、レジストリの関係を概要レベルで説明できる。
- VM とコンテナの違いを、管理対象、起動速度、配布単位の観点で説明できる。
- Azure Container Registry、Azure Container Instances、Azure Container Apps、AKS の大まかな位置づけを説明できる。
- Azure Portal で ACI を作成し、講師共有 ACR の NGINX イメージを使って Web サーバを公開できる。
- ACI の FQDN または IP アドレスを確認し、ブラウザーから NGINX にアクセスできる。
- ハンズオンで作成したリソースをリソースグループごと削除し、講師共有 ACR は削除対象に含めないことを理解できる。

## 受講後に説明できること/操作できること

- コンテナイメージはアプリケーションと実行に必要な内容をまとめた配布単位である、と説明できる。
- ACR はコンテナイメージを保管する場所、ACI はコンテナを実行する場所、と説明できる。
- Azure Portal で Container Instances を作成し、イメージ名、ポート、公開 DNS 名を設定できる。
- ACI の状態、FQDN、IP アドレス、ログまたはイベントを確認できる。
- 第3回の VM 構成と第4回の ACI 構成を比較し、どの管理対象が省略されたかを説明できる。

## ハンズオン手順案

### ハンズオンのゴール

Azure Portal から Azure Container Instances を作成し、講師共有 ACR にある NGINX コンテナイメージを実行します。
最後にブラウザーから `http://<FQDN>` または `http://<IP Address>` へアクセスし、NGINX のページが表示されることを確認します。

### 入力値

| 項目 | 値の例 | 備考 |
| --- | --- | --- |
| リージョン | Japan East | 利用できない場合は講師が代替リージョンを指定 |
| 受講者番号 | `s01` | 講師が事前に採番 |
| リソースグループ名 | `rg-azbeg-l04-s01` | `s01` は自分の受講者番号に置き換える |
| ACI 名 | `aci-azbeg-l04-s01` | コンテナグループ名として使う |
| DNS name label | `aci-azbeg-l04-s01-<講師指定の接尾辞>` | リージョン内で一意。講師が接尾辞ルールを案内する |
| OS type | Linux | NGINX コンテナを想定 |
| CPU/Memory | 1 vCPU / 1.5 GiB など | 講師が事前検証した低コスト値を指定 |
| 公開ポート | TCP 80 | HTTPS は本回では扱わない |
| 共有 ACR ログインサーバー | `<共有ACRログインサーバー>` | 講師が案内する。例は教材確定時に差し替える |
| イメージ名 | `azbeg/nginx-l04` | 講師共有 ACR に事前格納 |
| タグ | `<講師指定タグ>` | 例: `latest` または講座日付タグ |
| 完全なイメージ名 | `<共有ACRログインサーバー>/azbeg/nginx-l04:<講師指定タグ>` | Portal の UI に合わせて分割入力する場合がある |
| ACR 参照方式 | 講師が事前設定 | 受講者が秘密情報を扱わない方式を優先。採用方式は講師準備で確定 |
| タグ | `Course=AzureWorkshopForBeginners`, `Lesson=L04`, `StudentId=s01`, `Environment=Workshop` | `StudentId` は自分の番号に置き換える |

### 共有 ACR の前提

第4回では、受講者ごとの ACR は作成しません。
講師が共有 ACR に NGINX コンテナイメージを事前格納し、受講者が ACI から参照できるように準備します。

ドラフト段階では、次のいずれかの方式を講師が事前に確定する前提です。

- 学習用イメージのみを秘密情報なしで pull できるようにする。
- 受講者が秘密情報を画面に入力しない形で ACR 参照権限を付与する。
- やむを得ず読み取り専用 pull 情報を使う場合は、講座内だけで扱い、スクリーンショットや公開資料には一切残さない。

### コスト見積もり欄

概算コストは、講師が教材作成後に検証環境で1回通し実行し、実測値または Azure Pricing Calculator をもとに確定します。
ドラフト段階では次の欄を残します。

| 項目 | 見積もり | 確定方法 |
| --- | --- | --- |
| 受講者1人あたり | 講師検証後に確定 | ACI 実行時間、CPU/メモリ設定、診断設定有無をもとに計算 |
| 50名分 | 講師検証後に確定 | 受講者50名 + 講師/予備分を想定 |
| コスト注意 | ACI の削除漏れ、診断ログ、共有 ACR | 共有 ACR は講師管理リソースとして別管理 |

### 手順1: Azure Portal にサインインする

- 目的: 講師が用意したサブスクリプションで作業できる状態にする。
- アーキテクチャ上の位置: まだ受講者リソースは作らない。
- Azure Portal 操作: `https://portal.azure.com/` にアクセスし、講師指定のアカウントでサインインする。
- 入力値: なし。
- 期待状態: 対象サブスクリプションが選択できる。
- よくある失敗: 個人の別アカウントでサインインしている。対象サブスクリプションが見えない。

### 手順2: リソースグループを作成する

- 目的: 本回の受講者作成リソースをまとめて管理し、最後にまとめて削除できるようにする。
- アーキテクチャ上の位置: ACI を入れる外枠。
- Azure Portal 操作: Resource groups > Create を選ぶ。
- 入力値: `rg-azbeg-l04-<受講者番号>`、Region は Japan East。
- 期待状態: リソースグループの Overview が表示される。
- よくある失敗: 受講者番号を入れ忘れる。第3回のリソースグループ名を使い回す。別リージョンを選ぶ。

### 手順3: Container Instances の作成を開始する

- 目的: コンテナを実行する ACI を作成する。
- アーキテクチャ上の位置: Web 層に相当する NGINX コンテナの実行場所。
- Azure Portal 操作: 検索ボックスで Container Instances を開き、Create を選ぶ。
- 入力値: なし。
- 期待状態: Container Instances の作成ウィザードに進める。
- よくある失敗: Container Apps や Kubernetes Service を選んでしまう。

### 手順4: 基本情報を入力する

- 目的: ACI の名前、配置場所、OS 種別を決める。
- アーキテクチャ上の位置: ACI のコンテナグループ本体。
- Azure Portal 操作: Basics タブで Subscription、Resource group、Container name、Region、OS type を指定する。
- 入力値: `aci-azbeg-l04-<受講者番号>`、Japan East、Linux。
- 期待状態: 講師指定の値で次へ進める。
- よくある失敗: リージョンを間違える。名前に使用できない文字を入れる。受講者番号を入れ忘れる。

### 手順5: 共有 ACR のイメージを指定する

- 目的: 講師が用意した NGINX コンテナイメージを ACI で実行する。
- アーキテクチャ上の位置: 共有 ACR から ACI へのイメージ pull。
- Azure Portal 操作: Image source または Container image の設定で、講師指定の ACR ログインサーバー、イメージ名、タグを指定する。
- 入力値: `<共有ACRログインサーバー>/azbeg/nginx-l04:<講師指定タグ>`。
- 期待状態: 作成前検証に進める。
- よくある失敗: ACR ログインサーバー名を入れ忘れる。タグを間違える。`latest` と講師指定タグを取り違える。認証情報をスクリーンショットに写す。

### 手順6: CPU とメモリを確認する

- 目的: NGINX の簡単な表示確認に十分な小さなリソースで起動する。
- アーキテクチャ上の位置: ACI の実行リソース設定。
- Azure Portal 操作: Size、Resources、または同等の設定欄で CPU とメモリを確認する。
- 入力値: 講師指定値。例: 1 vCPU / 1.5 GiB。
- 期待状態: 高価な設定や不要な GPU 設定になっていない。
- よくある失敗: 既定値のままでもよい箇所を大きく変更してしまう。クォータ不足になる。

### 手順7: ネットワークと DNS ラベルを設定する

- 目的: ブラウザーから ACI に HTTP でアクセスできるようにする。
- アーキテクチャ上の位置: Internet から ACI への公開入口。
- Azure Portal 操作: Networking タブで Public を選び、TCP 80 を公開し、DNS name label を入力する。
- 入力値: `aci-azbeg-l04-<受講者番号>-<講師指定の接尾辞>`。
- 期待状態: FQDN が生成される設定になっている。
- よくある失敗: DNS ラベルが重複する。HTTP 80 を開け忘れる。Private を選んでしまう。

### 手順8: タグを設定し、作成する

- 目的: 講師がハンズオンリソースを識別しやすくし、作成前に設定を確認する。
- アーキテクチャ上の位置: 受講者作成リソースの管理情報。
- Azure Portal 操作: Tags タブでタグを入力し、Review + create で検証後に Create を選ぶ。
- 入力値: Course、Lesson、StudentId、Environment、DeleteAfter。
- 期待状態: Validation passed になり、Deployment succeeded まで進む。
- よくある失敗: タグの `StudentId` を自分の番号に置き換え忘れる。Validation エラーを読まずに進もうとする。

### 手順9: ACI の状態と FQDN を確認する

- 目的: コンテナが起動し、ブラウザーからアクセスする宛先が分かる状態にする。
- アーキテクチャ上の位置: ACI の実行状態と公開アドレス。
- Azure Portal 操作: ACI Overview を開き、Status、FQDN、IP address を確認する。
- 入力値: なし。
- 期待状態: Status が Running になり、FQDN または IP address が表示されている。
- よくある失敗: Provisioning 中にアクセスする。FQDN ではなく別の値をコピーする。

### 手順10: ブラウザーで NGINX にアクセスする

- 目的: ACI 上で NGINX コンテナが動作していることを確認する。
- アーキテクチャ上の位置: ブラウザーから ACI の FQDN、公開ポート、NGINX コンテナへの通信。
- Azure Portal 操作: Portal ではなくブラウザーの別タブで `http://<FQDN>` にアクセスする。
- 入力値: ACI Overview で確認した FQDN または IP address。
- 期待状態: NGINX のページが表示される。
- よくある失敗: `https://` でアクセスする。FQDN を間違える。DNS 反映を待たずに更新し続ける。

### 手順11: ログまたはイベントを確認する

- 目的: ACI でコンテナの起動状態を確認する入口を知る。
- アーキテクチャ上の位置: 実行中コンテナの状態確認。
- Azure Portal 操作: ACI の Logs、Events、Containers などの画面を開く。
- 入力値: なし。
- 期待状態: コンテナが起動していること、または起動時のイベントを確認できる。
- よくある失敗: ブラウザー表示だけを見て、Portal 側の状態確認をしない。

### 手順12: リソースグループ内のリソースを確認する

- 目的: ACI では VM のように個別の VM、Managed Disk、NIC が見えないことを確認する。
- アーキテクチャ上の位置: 受講者リソースグループ内の作成物。
- Azure Portal 操作: リソースグループの一覧に戻り、作成されたリソースを確認する。
- 入力値: なし。
- 期待状態: ACI リソースが表示される。共有 ACR は受講者リソースグループには含まれない。
- よくある失敗: 共有 ACR も自分の削除対象だと誤解する。

### 手順13: リソースグループを削除する

- 目的: ハンズオンで作成した課金対象を削除する。
- アーキテクチャ上の位置: 本回で受講者が作成した ACI。
- Azure Portal 操作: リソースグループの Delete resource group を選び、名前を入力して削除する。
- 入力値: `rg-azbeg-l04-<受講者番号>`。
- 期待状態: リソースグループが削除中または削除済みになる。
- よくある失敗: ACI を停止しただけで削除したつもりになる。共有 ACR を削除しようとする。別のリソースグループを削除しようとする。

## よくある失敗

### Container Apps や AKS を選んでしまう

原因:
Azure Portal には似た名前のコンテナサービスが複数あります。本回で作成するのは Azure Container Instances です。

対応:
作成画面のサービス名を確認します。誤って別サービスの作成画面を開いた場合は、作成せずに戻ります。

### 共有 ACR のイメージ名またはタグを間違える

原因:
ACR ログインサーバー名、リポジトリ名、タグのどれかが違うと、ACI がイメージを取得できません。

対応:
講師が提示した値をコピーして確認します。`latest` を使うか講師指定タグを使うかを混同しないようにします。

### ACR の参照権限が不足する

原因:
講師共有 ACR から pull するための権限または参照方式が正しく設定されていない可能性があります。

対応:
受講者側で秘密情報を推測して入力しないようにします。講師が共有 ACR の設定、AcrPull 相当の権限、または採用した参照方式を確認します。

### DNS name label が重複する

原因:
DNS ラベルはリージョン内で一意である必要があります。短い名前や教材例そのままの名前は衝突しやすくなります。

対応:
受講者番号と講師指定の接尾辞を含めます。衝突した場合は講師の指示に従って接尾辞を追加します。

### HTTP でアクセスできない

原因:
ACI がまだ Running ではない、FQDN を間違えている、`https://` でアクセスしている、TCP 80 を公開していない、イメージ取得に失敗している可能性があります。

対応:
ACI Overview、FQDN、公開ポート、Logs/Events を順に確認します。復旧に時間がかかる場合は講師デモに切り替えます。

### 共有 ACR を削除対象だと誤解する

原因:
本回では共有 ACR を利用しますが、受講者が作成したリソースではありません。

対応:
削除するのは `rg-azbeg-l04-<受講者番号>` のみです。共有 ACR や `rg-azbeg-shared` のような講師管理リソースは削除しません。

## 講師が見る確認ポイント

- 受講者が正しいサブスクリプションを選べていること。
- リソースグループ名に第4回と受講者番号が含まれていること。
- リージョンが Japan East、または講師指定の代替リージョンになっていること。
- Container Instances を選んでおり、Container Apps や AKS を作成していないこと。
- 共有 ACR のログインサーバー名、イメージ名、タグが講師指定値になっていること。
- ACR の認証情報や秘密情報が受講者のスクリーンショットやメモに残っていないこと。
- TCP 80 が公開され、DNS name label が一意になっていること。
- ACI Overview で Running になっていること。
- ブラウザーで NGINX のページが表示されること。
- 受講者が VM 構成との違いを説明できていること。
- 最後に受講者リソースグループだけを削除できていること。

## 復旧できない場合のスキップ手順

時間内に復旧できない場合は、手順の完了よりも VM とコンテナの違いの理解を優先します。

1. ACI 作成前の Validation エラーで止まる場合は、講師が画面を確認し、名前、リージョン、DNS ラベル、権限、クォータのどれが原因かを切り分ける。
2. Image pull で失敗する場合は、講師が共有 ACR のイメージ名、タグ、参照方式、権限を確認する。
3. クォータ不足の場合は、講師指定の代替リージョン、代替リソース設定、または講師デモに切り替える。
4. ACI は作成できたが HTTP 表示できない場合は、講師の完成済みデモ環境で NGINX 画面を見せる。
5. 受講者には L04-D15、L04-D18、L04-T03 を使って、ブラウザー、ACI、共有 ACR、VM との違いを確認させる。
6. 自分の環境で作成途中のリソースがある場合は、講師と一緒に受講者リソースグループ削除だけは完了させる。

## クリーンアップ手順

本回のハンズオンはその回で完結するため、原則として最後に受講者ごとのリソースグループを削除します。
講師共有 ACR は受講者の削除対象ではありません。

1. Azure Portal で Resource groups を開く。
2. `rg-azbeg-l04-<受講者番号>` を開く。
3. 削除対象が本回の受講者作成リソースだけであることを確認する。
4. Delete resource group を選ぶ。
5. 確認欄にリソースグループ名を入力する。
6. Delete を実行する。
7. Resource groups 一覧で対象リソースグループが削除済み、または削除中であることを確認する。
8. `rg-azbeg-shared` などの講師共有リソースグループや共有 ACR は削除しない。

注意:
ACI を停止しただけでは、設定や関連状態が残る場合があります。本回では停止ではなく、受講者リソースグループ削除を完了状態とします。

## 講師向け補足

- 第4回は、第3回の VM ハンズオンと比較して理解させることが重要。コンテナ技術そのものの詳細に入りすぎない。
- ACI は学習用のシンプルなコンテナ実行環境として扱い、本番アプリ基盤としての詳細な推奨構成は第5回以降の ACA や、必要に応じて AKS の話へ分ける。
- 共有 ACR の参照方式は講座前に必ず確定する。受講者が秘密情報を画面に入力しない方式を優先し、やむを得ず pull 情報を使う場合も公開資料やスクリーンショットには残さない。
- 共有 ACR に格納する NGINX イメージは、表示内容を講座用にカスタマイズしておくと第3回との比較がしやすい。
- Japan East で ACI が利用できること、50名 + 講師/予備分の同時作成に対してクォータが足りることを少なくとも1週間前に確認する。
- DNS name label は衝突しやすいため、講師が当日用の短い接尾辞を事前に決めておく。
- Azure Portal の ACI 作成画面は更新される可能性があるため、講座前にスクリーンショットと手順を通しで確認する。
- 第5回から第6回では受講者ごとに ACR を作成するため、第4回では「今回は共有 ACR、次回以降は自分の ACR」という違いを明確にする。
- 早く終えた受講者向けの別タグデプロイは任意とし、全員のアクセス確認と削除確認を優先する。
