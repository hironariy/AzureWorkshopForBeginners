Web アプリケーションの基本

Web アプリケーションは、ブラウザーからの要求を受け取り、サーバー側の処理を経て、HTML や JSON などの結果を返す一連の仕組みです。

1台ですべて動かす構成

小規模な構成では Web、アプリケーション、DB を1台に同居させることもあり、まずはこの単純な形から役割の違いを見ていきます。

モノリシック構成の利点と注意点

1台にまとめた構成は始めやすい一方で、規模が大きくなると拡張、障害対応、変更範囲の分離が難しくなるため、利点と注意点をセットで確認します。

観点 利点 注意点
構築 必要なサーバやネットワーク構成が少ない。 役割が同居するため、後から責任範囲を分けにくい。
通信 同じサーバ内で処理できるため、経路が単純。 障害が起きたとき、影響範囲が Web/AP/DB 全体へ広がりやすい。
運用 見る対象が少なく、初期学習で全体を追いやすい。 規模が大きくなると、一部だけを拡張・変更しにくい。

Web 3層アーキテクチャ

Web 3層では、利用者に近い入口、業務処理、データ管理を分け、どの処理をどの層が担当するかを論理的な役割として整理します。

Web 3層は必ず3台ではない

Web 3層はサーバー台数の指定ではなく役割分担の考え方なので、1台同居、複数台分離、マネージドサービス利用のどれでも表現できます。

処理の流れを追う

ブラウザーからの要求が Web 層で受け付けられ、AP 層で処理され、必要に応じて DB 層を参照して結果が返る流れを順番に追います。

Web 3層のメリットと注意点

層を分けると責任範囲や拡張単位を整理しやすくなりますが、その分だけ通信経路、認証、監視対象が増えることも理解します。

メリット
  • 層ごとに役割を説明しやすい。
  • Web、AP、DB を別々に拡張しやすい。
  • 担当範囲や変更範囲を分けやすい。
注意点
  • ネットワークや認証の設計が必要になる。
  • 監視する対象が増える。
  • 障害時に通信経路を追う力が必要になる。

Web 層の役割

Web 層は利用者から最初にアクセスされる入口であり、静的ファイルの配信、HTTP/HTTPS の受付、AP 層への転送などを担当します。

  • HTTP / HTTPS の要求を受ける。
  • HTML、CSS、画像などの静的ファイルを返す。
  • 必要に応じて AP 層へ処理を渡す。

静的コンテンツと動的コンテンツ

画面や画像のようにそのまま返せる静的コンテンツと、検索結果や Todo 一覧のように処理後に生成される動的コンテンツを区別します。

静的コンテンツ

ファイルをそのまま返す

HTML、CSS、JavaScript、画像など。内容は事前に用意されている。

動的コンテンツ

処理結果を返す

ログイン結果、注文結果、Todo 一覧、API レスポンスなど。AP 層や DB 層と連携する。

Web サーバの代表例

Web サーバには NGINX、Apache HTTP Server、IIS などがあり、第3回では Azure VM 上に NGINX を配置して入口の役割を体験します。

名前 よくある使われ方
NGINX 静的配信、リバースプロキシ、軽量な Web サーバ。
Apache HTTP Server 幅広い環境で使われる汎用 Web サーバ。
IIS Windows Server と組み合わせて使われる Web サーバ。

第3回では Public IP、NSG、Azure VM、NGINX をつなげ、インターネットから Web 層に到達できる状態を Azure Portal で確認します。

  • Public IP から VM にアクセスする。
  • NSG で HTTP 通信を許可する。
  • NGINX の画面が見えれば入口まで到達できている。

AP 層の役割

AP 層は利用者の入力や API リクエストを受け取り、入力チェック、業務ルール、DB への問い合わせなどアプリ固有の処理を担当します。

  • API リクエストを受け取る。
  • 入力チェックや業務ロジックを実行する。
  • 必要なデータを DB 層に問い合わせる。

AP サーバの代表例

AP 層の実装は Node.js、Java/Spring、.NET、Python/FastAPI など多様で、ここでは製品比較ではなく役割の違いに注目します。

例 位置づけ
Node.js JavaScript / TypeScript で API を実装する選択肢。
Java / Spring 業務アプリケーションでよく使われる実装基盤。
.NET Web API や業務処理を構築できる Microsoft 系の基盤。
Python / FastAPI 軽量な API やデータ処理と組み合わせやすい選択肢。

Web 層と AP 層の関係

Web 層と AP 層を分けることで、利用者の入口、静的配信、API 処理、業務ロジックを別々に変更・拡張しやすくなります。

DB 層の役割

DB 層はアプリケーションのデータを安全に保存し、検索、更新、同時アクセス、トランザクションなどを扱う信頼できるデータ管理場所です。

  • データの保存、検索、更新を担当する。
  • 同時アクセスや整合性を扱う。
  • アプリケーションにとって信頼できるデータ管理場所になる。

DB サーバの代表例

代表的な RDBMS には PostgreSQL、MySQL、SQL Server、Oracle Database があり、第5回から第6回では PostgreSQL を使います。

名前 補足
PostgreSQL 第5回から第6回で Azure Database for PostgreSQL として扱う。
MySQL Web アプリケーションで広く使われる RDBMS。
SQL Server Azure SQL Database など Microsoft のマネージド DB とつながる。
Oracle Database 大規模な基幹系システムで見かけることが多い。

AP 層と DB 層の関係

AP 層は自分でデータを保持せず、認証情報、接続設定、ネットワーク到達性を使って DB 層に問い合わせ、必要な結果を受け取ります。

第5回から第6回で作る DB 層

第5回から第6回では Azure Database for PostgreSQL を使い、Todo アプリのデータ保存を Azure のマネージド DB として扱います。

  • DB サーバを自分で構築する代わりに、Azure のマネージド DB を使う。
  • アプリケーションは DB に接続して Todo を保存する。

Azure IaaS で構成する Web 3層

Azure VM を使った IaaS 構成では、Web/AP/DB の各層を分けて配置し、ネットワーク、負荷分散、DB の高可用性を組み合わせます。

VM 構成で自分が管理する範囲

VM を使う構成では自由度が高い一方、OS、ミドルウェア、パッチ、監視、スケールなど利用者が設計・運用する範囲も広がります。

SPA という別の見方

SPA では画面表示の多くをブラウザー側で行い、静的ホスティング、API、データサービスを組み合わせる構成として Web 3層とは別の見方をします。

Static Web Apps で扱うこと

RDBMS と NoSQL

データベースはすべて同じではなく、表形式で整合性を重視する RDBMS と、柔軟なデータ構造や分散を得意とする NoSQL を使い分けます。

観点 RDBMS NoSQL
データの形 表、行、列を中心に整理する。 ドキュメント、キー値、グラフなど多様。
得意なこと 整合性が重要な業務データを扱いやすい。 柔軟なデータ構造や大規模分散に向く。
Azure の例 Azure SQL Database、Azure Database for PostgreSQL Azure Cosmos DB
