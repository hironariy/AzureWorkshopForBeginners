Azure の管理スコープ

Azure リソースは、管理グループ、サブスクリプション、リソースグループ、リソースという階層で管理します。

管理グループ複数サブスクリプションをまとめ、組織全体の Policy や RBAC の単位にできます。

タグはあとから効いてくる

タグは、コスト、所有者、環境、削除予定を追跡するためのメタデータです。運用で見返す前提で、表記ゆれを抑えて付けます。

RBAC と Policy の違い

RBAC は誰が操作できるか、Policy は作られた状態がルールに合うかを見ます。両方を組み合わせることで、権限と準拠性を分けて管理できます。

観点Azure RBACAzure Policy
主な問い誰が操作できるか作られた状態がルールに合っているか
対象ユーザー、グループ、アプリ、ワークロード IDAzure リソースの構成やプロパティ
例受講者がリソースグループを作成できるJapan East 以外を拒否する、タグ必須にする
関係操作権限を与える権限があってもルール違反なら拒否または監査できる

Defender for Cloud

Defender for Cloud は、クラウド環境のセキュリティ体制とワークロード保護を確認する入口です。単なるウイルス対策としてではなく、推奨事項の地図として見ます。

有料プラン有効化前に対象と費用を確認
DevSecOps存在紹介に留め、詳細は扱わない

セキュリティ推奨事項

推奨事項は、今すぐ直すべき構成の弱点を見つけるための出発点です。正解の自動適用ではなく、影響と費用を見て判断します。

観点確認すること初心者向けの言い換え
対象どのリソースに対する推奨か何が危ないと言われているか

影響変更するとアプリに影響するかすぐ直してよいか、検証が必要か
費用有料プランが必要か有効化前にコストを見る
所有者誰が対応するかセキュリティだけでなくアプリ担当も関係する

Key Vault

Key Vault は、シークレット、キー、証明書をアプリケーションや手順書から分離して管理します。置き場所だけでなく、アクセスする ID と権限が重要です。

アプリケーション接続文字列を直書きしない
→
Managed Identity / Service PrincipalEntra ID で認証
→
Key VaultSecret、Key、Certificate
  • コード、手順書、スクリーンショットに秘密情報を残さない。
  • 参照できるワークロードを RBAC またはアクセスポリシーで絞る。

Secret をどこに置くか

GitHub Secret、アプリ設定、Key Vault は用途が違います。デプロイ時の秘密情報と、実行時にアプリが参照する秘密情報を分けて考えます。

保管場所主な用途注意点
GitHub SecretGitHub Actions がデプロイ時に使う秘密情報リポジトリごとの管理。Azure 内の実行時秘密情報とは分ける
アプリ設定実行時の設定値をアプリに渡すシークレットを置く場合はアクセス管理と表示範囲に注意する
Key Vaultシークレット、キー、証明書を集中管理するアプリから参照するには ID と権限設計が必要

Azure Storage

Storage は、オブジェクト、ファイル、キュー、テーブル、ディスクなど、幅広いデータ保存の土台です。単一の「ファイル置き場」ではありません。

Storage の代表的な使い分け

保存したいデータの形とアクセス方法によって、Storage 内でも選ぶサービスが変わります。Database とは目的を分けて考えます。

サービス向いているデータ例

Storage はセキュリティと冗長性も考える

Azure Backup

Backup は、過去の時点に戻せる復旧ポイントを保持するためのサービスです。バックアップがあることと、戻せることは分けて確認します。

対象リソースVM、Files、Blob、対応 DB など
→

Azure Site Recovery

Site Recovery は、障害時に別の場所でワークロードを起動して業務継続するための DR サービスです。バックアップではなく、レプリケーションとフェールオーバーを扱います。

プライマリ環境Azure VM / オンプレミス VM
→
継続的なレプリケーションRecovery Services vault で管理
→
セカンダリ環境別リージョンや Azure 環境
→
フェールオーバー計画、計画外、テスト

フェールオーバーは既定で完全自動とは考えず、運用判断、復旧計画、訓練を含めて設計します。

Backup と DR は目的が違う

Backup は戻るため、DR は続けるための設計です。必要な要件も確認する指標も異なります。

観点BackupDR / Site Recovery
主な目的過去の復旧ポイントから戻す障害時に別の場所で起動し、業務を継続する
主な障害シナリオ誤削除、データ破損、ランサムウェアリージョン障害、サイト停止、大規模な基盤障害
重視する指標どの時点まで戻せるか、保持期間、復元粒度RTO、RPO、切り替え手順、ネットワーク、復旧訓練
注意点バックアップがあっても復元に時間がかかる場合があるレプリケーションは論理破損も複製する場合がある

何を保護するか

VM、ファイル、データベース、Blob、オンプレミス VM など、対象によって Backup と Site Recovery の使い分けが変わります。

サービス代表的な対象注意点
Azure BackupAzure VM、Managed Disk、Azure Files、Blob Storage、対応するデータベースなど対象サービスごとに方式、保持、復元粒度が異なる
Azure Site RecoveryAzure VM のリージョン間 DR、オンプレミス VMware/Hyper-V VM、物理サーバーから Azure への DR など対象、リージョン、ネットワーク、フェールバック可否を事前確認する
サービス固有のバックアップPostgreSQL、SQL Database、Storage などの組み込みバックアップ機能Azure Backup だけでなく、サービス標準機能も確認する
アプリケーション側の保護DB レプリケーション、エクスポート、アプリ固有の復旧機能Azure サービスだけで完結しない場合がある
