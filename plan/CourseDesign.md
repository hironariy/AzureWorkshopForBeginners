# Azure Workshop for Beginners 教材全体設計

## 目的

この文書は、`InitialRequirement.md` をもとに教材制作へ進むための全体設計を定義するものです。
各回の Markdown ドラフトを作成する前に、講座全体の学習ストーリー、教材構造、制作順序、レビュー観点、図表とスクリーンショットの扱いをそろえます。

## 設計の前提

- 講座は Azure 未経験者でも参加できるが、オンプレミスまたは Azure でのシステム開発経験がある受講者を想定する。
- オンライン講座は1回60分で、基本構成は50分レクチャーまたはハンズオン、10分QAとする。
- ハンズオンは Azure Portal を中心に構成し、IaC は使わない。
- Azure CLI を使う場合は Azure Cloud Shell からのみ利用する。
- 最大受講者数は50名とする。
- 講師が用意する Azure サブスクリプションをハンズオンで共有し、講師は受講者にサブスクリプションスコープの Contributor ロールを事前付与する。
- 受講者は Microsoft Entra ID アプリ登録と Service Principal 作成を実行できる前提とする。
- 第4回は Azure Container Instances を使った Web サーバ構築に固定する。
- 第5回から第6回は Azure Container Apps と Azure Database for PostgreSQL を使った Todo アプリ構築に固定する。
- 第1回は最後に制作する。まず第2回から第11回の Markdown ドラフトを順次制作し、最後に第1回で全体の導入として整える。
- 第12回はオフサイトの座学 + ハンズオンだが、サンプルアプリケーションが未完成のため教材開発は後回しにする。

## 未確定事項と設計上の仮置き

次の項目は `InitialRequirement.md` の未決事項として残っているため、教材設計上は仮置きで進めます。

- コスト上限: 1人あたり、全体とも未確定。各ハンズオン教材ではコスト見積もり欄を必ず用意し、検証後に数値を入れる。
- 講師用・予備アカウント数: 最大受講者数は50名で確定済み。クォータ計算は `50名 + 講師用 + 20%予備` で記述できる形にする。

## 講座全体の学習ストーリー

講座全体は、単なるサービス紹介ではなく「Web システムを Azure 上で段階的に理解し、最後に運用・設計・AI まで視野を広げる」構成にします。

1. クラウドで設計する意味を知る。
2. Web 3層アーキテクチャという共通言語を持つ。
3. VM で Web サーバを作り、IaaS の構成要素を体験する。
4. ACI で Web サーバを作り、コンテナによる簡略化を体験する。
5. ACA と PostgreSQL で複数サービスを組み合わせたアプリ構成を作る。
6. 作った構成をネットワーク、周辺サービス、SPA、AI、監視の観点で見直す。
7. オフサイトで AI アプリ構築に接続する。

## 学習フェーズ

| フェーズ | 対象回 | 主な狙い | 受講者の状態 |
| --- | --- | --- | --- |
| 導入 | 第1回 | クラウド設計の重要性を理解する | 講座全体の地図を持つ |
| アーキテクチャ理解 | 第2回 | Web 3層の基本を理解する | 以降のハンズオンで何を作るか説明できる |
| 単体実行基盤 | 第3回、第4回 | VM とコンテナの違いを体験する | Azure Portal で単純な Web サーバを作れる |
| 複合アプリ構築 | 第5回、第6回 | Web/API/DB のアプリ構成を体験する | 複数 Azure サービスの関係を説明できる |
| 設計と運用の拡張 | 第7回から第11回 | ネットワーク、周辺サービス、SPA、AI、監視を整理する | 実案件で何を検討すべきか見通せる |
| 実践統合 | 第12回 | AI アプリ構築を体験する | クラウドネイティブな AI アプリの構成を説明できる |

## 教材の標準構成

各回の Markdown ドラフトは、原則として次の構成にします。座学回とハンズオン回で不要な項目は省略せず、「本回では扱わない」と明記します。

1. 表紙
2. この回の位置づけ
3. 受講前提
4. 到達目標
5. 受講後に説明できること/操作できること
6. 本回で扱う範囲
7. 本回で扱わない範囲
8. セクション構成
9. 解説スライド案
10. 図表案
11. スクリーンショット取得指示
12. ハンズオン手順案
13. よくある失敗
14. 講師が見る確認ポイント
15. 復旧できない場合のスキップ手順
16. クリーンアップ手順
17. 振り返り
18. 講師向け補足
19. 参考資料

## スライド設計パターン

### 説明スライド

- 目的: 概念やサービスの意味を理解させる。
- 構成: タイトル、リード文、図表、補足箇条書き。
- 制約: 本文は日本語200文字以内を目安にし、1枚のスライドでは1つの主張に絞る。

### 比較スライド

- 目的: VM とコンテナ、Web 3層と SPA、診断設定と Azure Monitor Agent などの違いを理解させる。
- 構成: 比較表、判断軸、使い分けの一言。
- 制約: 比較軸は5つ以内を基本にする。

### アーキテクチャスライド

- 目的: サービス間の関係、通信経路、責任分界を理解させる。
- 構成: 図、主要な通信、受講者が今回作る範囲、講師が事前準備する範囲。
- 制約: 作成済み、今回作成、未作成の状態をラベルで明確にする。

### ハンズオン手順スライド

- 目的: 受講者が迷わず操作できるようにする。
- 構成: スクリーンショット、操作箇所の吹き出し、入力値、確認状態。
- 制約: 1スライド1操作を基本とする。スクリーンショットは筆者が取得し、AI は吹き出し文と説明文を作成する。

### トラブルシューティングスライド

- 目的: つまずいた受講者を講座内で復帰させる。
- 構成: 症状、原因候補、確認箇所、復旧手順、復旧できない場合のスキップ手順。
- 制約: 講師が短時間で判断できる粒度にする。

## 図表設計方針

図表は受講者の理解を助けるための主役として扱います。単なる装飾として図を置かず、各図に明確な学習目的を持たせます。

必須で図表化するもの:

- Web 3層アーキテクチャ
- Azure VM と関連リソースの関係
- VM と ACI の比較
- ACA + PostgreSQL Todo アプリ全体構成
- Hub & Spoke ネットワーク構成
- Private Endpoint と DNS の名前解決シーケンス
- Static Web Apps + Functions + DB の SPA 構成
- AI エージェントの構成要素
- Azure Monitor、Log Analytics、Application Insights、診断設定、Azure Monitor Agent の関係

図表作成ルール:

- Azure アイコンは draw.io 内蔵 Azure SVG アイコンを `img/lib/azure2/` の参照パスで利用する。
- アイコンのテキスト背景色は設定しない。
- 図は SVG としてエクスポートし、スライドや HTML に挿入する。
- 通信経路は矢印、管理対象の範囲は枠、受講者作業範囲はラベルで示す。
- 色だけで意味を伝えず、ラベルや線種も併用する。

## スクリーンショット設計方針

スクリーンショットが必要なスライドでは、教材本文に実画像を仮置きせず、筆者に対する取得指示を記述します。

スクリーンショット指示には、必ず次を含めます。

- 対象サービス名
- Azure Portal の画面名
- 取得するタイミング
- クリック箇所
- 入力値
- 確認すべき状態
- マスクすべき情報

マスク対象:

- サブスクリプション ID
- テナント ID
- ユーザー名
- メールアドレス
- シークレット
- 接続文字列
- Service Principal の認証情報
- 課金情報

## ハンズオン設計方針

ハンズオンは、単に手順をこなすものではなく「アーキテクチャのどの部分を作ったか」を毎回確認できるようにします。

各ハンズオンセクションでは、次をセットにします。

1. いま作るもの
2. アーキテクチャ上の位置
3. Azure Portal の操作
4. 入力値
5. 作成後の確認
6. よくある失敗
7. 次の手順との関係

## 講師向け資料の標準構成

講師向け資料は受講生向け教材と分けて作成します。各回の講師向け資料は次の構成にします。

1. この回の狙い
2. 受講者がつまずきやすいポイント
3. 強調して説明するポイント
4. 時間配分
5. 事前準備チェックリスト

7. コスト注意点
8. トラブルシューティング
9. スキップ手順
10. QA 想定問答

## レビューゲート

### Gate 1: Markdown ドラフトレビュー

確認すること:

- 要件と矛盾していないか。
- 1時間の講座として過剰ではないか。
- 必須、時間があれば触れる、参考資料の切り分けが明確か。
- 図表案とスクリーンショット指示が十分か。
- ハンズオンのクリーンアップが明記されているか。

### Gate 2: HTML 詳細版レビュー

確認すること:

- GitHub Pages 上で読みやすいか。
- 図表、表、スクリーンショット指示がレビューしやすいか。
- アクセシビリティに問題がないか。
- 受講者が自習しても理解できる説明量になっているか。

### Gate 3: HTML プレゼンテーション版レビュー

確認すること:

- 1スライド1主張になっているか。
- リード文があるか。
- 文字量が多すぎないか。
- 図表と本文の対応が明確か。
- 講師が50分で説明できる枚数か。

### Gate 4: Microsoft 365 Copilot Cowork プロンプトレビュー

確認すること:

- 生成したい PowerPoint の構成が明確か。
- 添付する参考ファイルが指定されているか。
- アクセシビリティ、色、フォントサイズ、図表配置の指示が入っているか。
- PowerPoint 生成後の人間レビュー観点が入っているか。

### Gate 5: 公開前レビュー

確認すること:

- MIT ライセンスで公開してよい内容だけになっているか。
- 個人情報、サブスクリプション ID、テナント ID、シークレット、接続文字列が含まれていないか。
- 外部資料の扱いが適切か。
- 第9回の Microsoft 公式サンプルアプリの参照先が存在しているか。
- Azure 利用料金に関する注意書きがあるか。
